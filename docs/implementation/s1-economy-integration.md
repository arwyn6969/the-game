# S1 activation handoff

S1 supplies an optional `Town.economy` extension and reviewable engine helpers. Ordinary creation, loading and play do not initialize it. This is deliberate: S2 must activate every money adapter, funded work and matching player terms together. Passing these helper tests does not make the current live economy fully accounted or fair.

## Single boundary and recovery

`initializeFundedEconomy(town)` is the explicit initialization boundary. It works on a clone, preserves valid original purses and tills (including values above the legacy caps), records those values as opening balances, classifies existing payroll evidence and protects fundable payroll. It commits only validated state. Migration creates no income and reconstructs no lost earnings. Repeated initialization validates existing books without recreating them.

`importFundedTown(text)` applies that boundary to a raw or wrapped version-1 file. `readTownFile(text)` reads without activating missing extensions. Both detailed APIs return the complete original text and a reason on failure. `parseTownFile`, `readTownSave`, `loadTown`, `saveTown`, and `exportTown` keep their existing signatures. Present extensions are audited before old repairs can clamp balances or rename financial records. Inconsistent saves are rejected; `saveTownWithStatus` does not replace the stored backup with inconsistent books. Export remains usable to download the current raw state for recovery.

The extension adds account openings, a transfer journal, holds, quoted terms, command receipts, funded work and project custody. Account IDs address the original personal purses and business tills; openings are historical snapshots, not an alternative mutable cash balance. Per-account reconciliation detects unrecorded transfers even when total money stays constant. Downgrade round trips are unsupported: an older runtime may strip the extension entirely or alter balances without maintaining it. A retained but inconsistent extension fails validation; once stripped, an old file cannot prove its lost obligations and must not be presented as a verified ledger continuation.

## Integration contract and next packet

Use account queries for balance, active holds and available funds; payroll/project queries add unavailable funding reasons. Funded work exposes the offer's worker, payer, fee, evidence requirements, expiry and cancellation terms; accepted agreements retain progress, completion receipts and earned payables. Settlement records money moved separately from the work receipt and its successful, failed or uncertain outcome. Use returned command receipts to derive memories; never derive financial state from memory prose. Rejections contain a stable code and a reason suitable for translating into ordinary player copy.

S2 owns the authored three-record fixture, evidence cards/box observations, ordinary-control project discovery, two donor approvals, task consent, truthful index labels, Northern's routed independent lookup and complete receipts/budget UI. It also owns the complete replacement of the old wage/debt/midnight paths above. Keep S2 pending until S1 is reviewed and the integration owner has a stable visual baseline. PR #11 was merged into main before this checkout was created; its source is preserved in the S1 branch's main merge. No new visual integration is included in S1.

Do not enable `Town.economy` in a published town while running the old money paths: audit rejection is a recovery guard, not an adapter. The helper-only packet does not remove the current top-ups, change existing live shift promises, provide cross-device accounts or establish long-term economic fairness.
