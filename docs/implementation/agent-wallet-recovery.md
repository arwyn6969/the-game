# Agent wallet recovery and acceptance policy

Policy and evidence as of 16 October 2026. This supplements the [private owner registry](agent-receiving-registry.md) and its later receiving/deposit gate. It hardens provider linking while preserving the existing providers, normal sign-in, bearer/preview transports and explicit linking. It does not enable public funding, create a recovery endpoint, or grant permission to move BTC or stamps.

## Three separate things to recover

| Item                                           | Authority and backup                                           | What another backup cannot replace                                                                                       |
| ---------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Local town, memories and narrative IDs         | A validated Town export and existing browser recovery copies   | A game file does not authenticate an account or prove wallet control                                                     |
| Private registered copy and receiving profiles | The authenticated account and coherent server database backups | A matching name, email, imported world, stamp or copied registration ID does not constitute a new recovery authorization |
| External wallet and its assets                 | Keys and recovery procedure retained in the external wallet    | The game has no seed, private key or mechanism to recover or spend those assets                                          |

The owner retains the external wallet keys. The game stores watch-only address assignments and observations. Signing an address challenge does not authorize an outgoing transaction, transfer private character history, or establish control of a game account. Every future outgoing transfer still requires owner approval of the exact transaction.

## Account-linking hardening and remaining broker trust

The registry authenticates the application's Better Auth user ID, not an independently verified broker subject. Every private request checks the live session and the account reference expected by the panel. That prevents revoked-cache and stale displayed-account/live-token mismatches. It does not redefine which identities the platform may link to one Better Auth user.

The [auth configuration](../../src/lib/auth/server.ts) now sets `accountLinking.disableImplicitLinking: true`. A new provider identity cannot automatically join an existing account because its email matches, even if the provider is trusted or the email is verified. The existing `enabled`, trusted-provider list and `requireLocalEmailVerified: false` settings remain; the explicit-only flag prevents those settings from permitting an implicit alias.

The [OAuth policy tests](../../scripts/agent-identity-policy.test.mjs) run the actual app auth route, generated OAuth state, token exchange, callback, database adapter, signed session and strict owner guard. Only a disposable broker's token and user-info responses are fixtures; no external broker or personal account is contacted.

Before hardening, nine passing characterization cases reproduced the following behavior in Better Auth 1.6.33 under the previous configuration. This table records the **historical finding**, not the release behavior:

| Fixture input                                                                                        | Observed result                                           |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Same provider and same subject signing in again                                                      | Same Better Auth user ID                                  |
| Distinct Google/X provider subjects with the same reported email                                     | Both link to the same Better Auth user ID                 |
| Existing/incoming email verification flags `false/false`, `false/true`, `true/false`, or `true/true` | Linking succeeds in all four combinations                 |
| Distinct subjects from the same trusted provider with the same reported email                        | Both link to the same Better Auth user ID                 |
| Distinct subjects and distinct reported emails                                                       | Independent Better Auth users                             |
| An already linked provider subject reports a different email                                         | Existing Better Auth user ID is retained                  |
| Invalid OAuth state                                                                                  | Rejected before the token exchange; no account is created |

The current regression suite verifies the fix: all four same-email verification combinations and the same-provider/different-subject case return `account_not_linked`, create no new provider binding or session, and cannot satisfy the owner guard. The original provider subject still signs in. A person must sign in through the established identity before using the platform's authenticated explicit-linking API; a newly attempted alternate provider with a matching email cannot supply that authority. There is no new provider-linking or recovery UI in the game panel.

The audit also reproduced sensitive-link session gaps. A signed cookie cache could initiate `/oauth2/link` after its database session was revoked, and an already pending callback could persist a binding after revocation, logout or a switch to another account. The catch-all now requires a live session before either linking-initiation endpoint and strips only the configured session-data cache cookie and its chunks from the forwarded linking-start request. This makes the underlying linker use the same live cookie/bearer owner instead of a stale cached account. Other cookies, credentials, request bodies and normal auth caching are preserved. Before creating or updating a provider binding, account hooks inspect only Better Auth's own validated OAuth linking state and require an authoritative current session for that same initiating user. Ordinary sign-in/signup callbacks have no linking state and continue to work. No raw OAuth-state payload is parsed or trusted by application code.

Valid authenticated explicit linking, fresh sign-in through an existing linked identity, bearer-based linking initiation, and normal first sign-in remain covered. Previously linked account rows are preserved; this change does not audit, remove or retrospectively reauthorize old aliases. Existing bindings need review if there is evidence of past account compromise.

The fixture does not demonstrate that a real attacker can make the broker assert another person's email or subject. The real broker must still authenticate stable provider identities and protect its own account recovery process. Blocking new email-based automatic links does not establish that upstream recovery is email-independent or that a provider will never reassign a subject.

Before public funding or any ownership-transfer capability, establish and record the real broker's subject, email-verification, alias, provider-linking and account-recovery guarantees. If those guarantees do not meet the required ownership boundary, design a registry-specific principal/recovery mechanism and review its migration explicitly. The narrow hardening above adds no account recovery override.

## Conservative recovery rules

1. **No new recovery override exists.** Support must not reassign a registration or address because someone supplies a matching email, Town file, character name, stamp, transaction history, screenshot, or signature from an externally linked wallet. Newly attempted provider identities cannot join an existing owner by matching email; existing provider bindings remain the platform's sign-in authority.
2. **Normal account recovery must return the established account.** Recover access through the account/provider's supported process. A different Better Auth user ID receives its own private namespace; it does not inherit another account's registrations. Any future extra recovery factor must be enrolled while the original account is authenticated, independently verified, and designed before it is relied on. No such factor or transfer workflow is implemented today.
3. **Keep funded destinations bound to their original receiving profile.** Every old address reservation survives replacement, retirement and account deletion. Reproof can reactivate an address only for that same profile. A new account or imported copy must use new addresses; a fresh wallet signature alone cannot take over an old profile or its private character history.
4. **Treat lost wallet keys separately.** The owner may restore the external wallet locally using its existing backup procedure. Never paste a seed, key, wallet backup or recovery code into the game, a prompt, issue, test fixture or support message. If the owner cannot restore those keys, the game cannot recover the assets. An authenticated owner may retire the old draft and prove a new external address; old destinations stay reserved and old assets do not move automatically.
5. **Retirement does not stop incoming payments.** It stops use of that draft in the game. A sender may still use an old address independently. Later observers must retain historical profile/address associations and must not credit late arrivals to a replacement resident, account or fork. Public funding remains disabled until its separate acceptance gates pass.
6. **Account deletion is not account migration.** Deletion removes the private registry while preserving address tombstones. No current UI can reclaim the deleted profile under a new account. A support request must not remove tombstones to make an address available again.
7. **Restore server state coherently.** A database recovery plan must preserve auth user/account identity, registrations, residents, profiles, all address reservations, and any later observation records together. Restoring only a town or only active profiles cannot safely recreate ownership. Revoke sessions after a security recovery as appropriate, retain audit evidence, and reconcile later chain observations from canonical sources. Stable auth secrets and provider credentials belong in the operator's existing protected secret management, never repository files or Town exports.
8. **Do not promise narrative recovery from wallet data.** The current panel finds a private registration using a matching local source world/roster. It does not provide an account-wide restoration browser, recover a deleted local town, or attach a new narrative world to an old receiving profile. Back up the town, server state and external wallet separately.

Any later transfer of a character or account to another person is a separate product operation. It must have explicit permissions, privacy rules, audit and settlement behavior; it must not be disguised as recovery. What transfers with a sold identity stamp remains undecided.

## Read-only observation permissions

Later BTC or protocol event observations may be implemented and tested while funding remains unpublished. Reading public chain data does not make its association with a private resident public.

- Resolve the live account and expected-owner precondition on every private read. Scope through the account's registration and profile; a known profile ID or public source world ID is never a read capability. Return `Cache-Control: private, no-store` and keep existing Origin/Fetch Metadata isolation.
- Fetch only registered/reserved addresses through fixed validated adapters. Do not accept arbitrary remote URLs or expose a global browser endpoint for all watched addresses. A background observer's ingestion permissions must not grant a browser access to another owner's records.
- Associate events with the immutable network/address/profile reservation, including historical addresses. Check current owner and request context before displaying a delayed result. Replacement or retirement must not remap old events or reveal another account's data.
- Keep protocol event identity and BTC outpoint identity separate. Record pending, confirmed, dropped/replaced and reorganized observations as supported by the source; make reconciliation idempotent. Holdings changes alone are not deposit receipts. Outages or incomplete history remain unknown or stale, never fabricated zero balances.
- Observed BTC, confirmed BTC and spendable fee funds are different claims. Read-only observations do not authorize spending or establish that an asset-bearing output is safe to spend. No observation becomes town coins, model authority, a trading balance, or public payment instructions.
- Keep private address associations, session material and event details out of Town exports, prompts, memories, analytics, ordinary logs and public profiles. Define a reviewed, explicit public projection later instead of exposing the private registry wholesale.

Owner-tool preview credentials travel only in the `Authorization` request header. The installed TanStack transport serializes `sendContext` into GET URLs, so these private functions must never forward session material through that context. A captured-fetch regression covers real header/cookie sessions, signed-out and revoked requests, and absence of credentials from the GET URL. The inherited generic `src/lib/auth/middleware.ts` still uses serialized bearer context outside the owner-tool scope; it requires a separate transport review before bearer-authenticated GET functions rely on it. This packet does not change that shared middleware.

### Genuine OAuth acceptance

Use a reviewed staging origin with legitimately configured sign-in and persistent test storage. Do not provision or publish production settings solely to mark this checklist complete.

1. Record the tested commit, origin, date, browser, provider path and an opaque account reference. Keep credentials, cookies, bearer tokens, authorization codes and identity payloads out of the receipt.
2. Complete each supported real sign-in path and return to the exact app origin. Verify the account shown and the owner reference used by private operations match. Check both a fresh browser and a returning session; verify persistence after a controlled staging server restart.
3. Use two real test identities. Confirm documented behavior for provider switching, cancellation and popup blocking where applicable. A new alternate identity sharing an email must not inherit the account: sign in through the original provider first and use only the platform's authenticated explicit-linking workflow if available. Confirm a pending link stops after logout, revocation or an account switch. Obtain the broker's contract for subject stability, verification of emails and existing account aliases; do not infer it from displayed email strings.
4. Confirm account A cannot see or mutate account B's registrations, including the same imported Town IDs. Exercise logout, revoked sessions, cached cookies, another open tab and pending requests. A failed logout must stay visibly unconfirmed with private data hidden until explicit recovery.
5. Verify the supported account recovery process returns the intended established account. Do not invent a game support override if the provider returns a new account. Record unresolved linking/recovery behavior as pending.

### Preferred wallet and external-backup acceptance

The preferred recommendation is [Wonder Wallet](https://wonder-wallet.com), per the 16 October product direction. Its adapter and compatibility checks remain future work; the actual acceptance receipt above applies only to Leather. Run the same account selection, exact-message, cancellation, retirement and backup/restore checks for Wonder Wallet before presenting it as a supported default. Preserve the verified Leather path while that work is completed.

Use a disposable wallet controlled by the human tester. The game must never receive its seed or keys. Address lookup and message signatures can be tested without moving funds.

1. Record the exact browser/OS and Leather extension version and mainnet Native SegWit address type. Confirm the extension's account selector and the address returned to the game agree.
2. Select two distinct wallet accounts and link two different residents. Review each fresh message in Leather: exact origin, authenticated owner reference, registration, resident, profile, revision, address, nonce, expiry and watch-only purpose. Confirm the signature verifies for the displayed address and never requests a PSBT, send, trade or spending approval.
3. Exercise wallet rejection, cancellation, wrong network/account, expiry, retry and a delayed wallet response after changing resident or closing the panel. Confirm stale results do not update a different resident.
4. Retire/replace a draft and verify old-address reuse by another resident/account remains blocked. Confirm the external wallet is unaffected and the game does not advertise deposits or claim a zero balance after an indexer outage.
5. Following the wallet's own documented recovery procedure locally, restore the disposable backup in a separate wallet profile/device under the tester's control. Prove the same receiving address with a newly issued message for the original profile. Record only the result and public compatibility information; never reveal backup material.
6. Separately establish compatibility with the selected classic Stamp/Counterparty asset protocol, historical event lookup and protected outputs before accepting deposits. A successful P2WPKH message signature does not prove asset-aware receiving, coin selection or trading support. No live transfer is authorized by this checklist.

A manual receipt should mark each item **passed**, **failed**, or **pending**, identify the tested versions/commit and link sanitized evidence. Missing access to a real provider, extension or retained backup remains pending; a simulated result cannot close it.
